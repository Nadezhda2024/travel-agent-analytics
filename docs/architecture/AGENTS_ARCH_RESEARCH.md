1. Введение и постановка проблемы
Основная техническая сложность при создании AI-агента для путешествий в рамках трека «О!дин запрос» заключается в необходимости связать свободный ввод пользователя на естественном языке с детерминированным вызовом программных функций поиска и формирования корзины. Поскольку организаторы не предоставляют готовых API, вся логика извлечения намерений, фильтрации, подбора и сборки должна быть спроектирована внутри нашей системы. Для решения этой задачи в мировой практике open-source разработки выделились три базовых архитектурных паттерна.
2. Архитектурный метод 1: Детерминированные графы состояний (Deterministic State Machines)
Логика работы: При данном подходе весь жизненный цикл сессии пользователя разбивается на строгие, последовательные программные узлы (Понимание, Вдохновение, Подбор, Объяснение, Сборка, Пересборка), которые зашиваются непосредственно в бэкенд-код. Большая языковая модель (LLM) не принимает самостоятельных решений о том, какое действие совершить дальше. Она вызывается изолированно внутри каждого узла как инструмент трансформации данных. Например, на этапе 'Понимание' LLM переводит текст пользователя в структурированный JSON с фильтрами, а бэкенд проверяет этот JSON на полноту с помощью валидационных контрактов (Pydantic или Zod). Если данных не хватает, код принудительно возвращает систему на узел уточнения.
Оформление в коде и требования: В репозитории фиксируется глобальный объект состояния сессии (State), хранящий историю сообщений, текущие фильтры и ID подобранных сущностей. Переходы между узлами графа описываются жесткими условными операторами в коде.
Преимущества: Полное отсутствие непредсказуемого поведения. Система никогда не вызовет функцию поиска отелей, если не валидирован регион или даты, что гарантирует высокую отказоустойчивость.
Недостатки: Снижение гибкости диалога. Если пользователь захочет резко изменить тему разговора, системе потребуются сложные предописанные обходные пути и циклы в коде графа.
3. Архитектурный метод 2: Многоагентные системы (Multi-Agent Systems)
Логика работы: Архитектура строится на базе ансамбля специализированных ИИ-агентов под управлением центрального диспетчера (Supervisor). Главный агент принимает запрос, анализирует его с помощью LLM и решает, кому делегировать задачу. Субагенты (например, Агент-Отели, Агент-Транспорт, Агент-Погода) обладают собственными изолированными промптами и доступом к конкретным инструментам (Function Calling). Память контекста и итоговая корзина склеиваются центральным оркестратором после того, как все субагенты вернут свои структурированные ответы.
Оформление в коде и требования: Каждый агент описывается как отдельный класс или конфигурационный промпт. Взаимодействие между ними реализуется через обмен сообщениями внутри фреймворков автоматизации ИИ (таких как CrewAI или LangChain).
Преимущества: Высокая модульность и масштабируемость системы. Разработчики могут независимо настраивать логику и промпты для каждого субагента, добавляя новые сущности без изменения ядра системы.
Недостатки: Высокая задержка ответов (Latency) из-за последовательных множественных вызовов LLM. Повышенный расход токенов и риск потери контекста при передаче данных между агентами.
4. Архитектурный метод 3: Синхронизация состояния интерфейса и чата (Generative UI)
Логика работы: Данный метод решает проблему рассинхронизации текстового диалога и графического интерфейса. Приложении отказывается от передачи сырого текста в пользу генерации структурированных событий (Events). Когда пользователь пишет запрос, LLM через Function Calling генерирует команду изменения состояния фронтенда. Сами расчеты цен, валидация корзины и логика пересборки происходят на бэкенде классическими программными методами, а LLM выступает лишь интеллектуальным триггером.
Оформление в коде и требования: Описывается жесткий контракт API эндпоинтов, где каждый ответ бэкенда содержит массив инструкций для рендеринга конкретных визуальных компонентов интерфейса в режиме реального времени.
Преимущества: Лучший пользовательский опыт (UX). Карточки отелей и билетов интерактивны, корзина обновляется мгновенно, а агент комментирует изменения естественным языком.
Недостатки: Экстремально высокая сложность разработки фронтенд и бэкенд частей. Требуется бесшовная интеграция ИИ с компонентами интерфейса, что трудно реализуемо в сжатые сроки хакатона.
5. Заключение и рекомендации
Учитывая ограничения хакатона (короткие сроки, команда из новичков, отсутствие готовых внешних API и необходимость развертывания локально в Docker одной командой), наиболее прагматичным и выигрышным решением является Метод 1 (Детерминированные графы состояний) с элементами Метода 3 для вывода карточек. Это позволит написать стабильный бэкенд на Python, четко понимать структуру ожидаемого JSON для рендеринга корзины, а так же контролировать продуктовые метрики без риска критических сбоев LLM во время демонстрации экспертам.
