Техническое задание: 
Сбор и структурирование требований
AI-агент для путешествий «О!дин запрос»
1. Бизнес-контекст и пользовательские истории
Настоящий документ определяет требования к первому шагу реализации архитектуры ИИ-ассистента в рамках хакатона Ostrovok 2026. Основная задача аналитика на данном этапе заключается в переводе абстрактных текстовых запросов пользователей в детерминированную структуру данных, пригодную для обработки программными методами бэкенда без риска галлюцинаций нейросети.
User Story (Пользовательская история)
Как самостоятельный путешественник, я хочу отправить один текстовый запрос на естественном языке, содержащий мои хаотичные пожелания, чтобы мгновенно получить сбалансированный, посчитанный тур (билеты, проживание, трансфер) с прозрачным текстовым объяснением выбора, не тратя время на ручной поиск по десяткам разрозненных сайтов.
2. Функциональные требования по 6 этапам работы агента
Логика взаимодействия ИИ-агента с пользователем и базой данных жестко разбита на шесть последовательных технологических этапов:
•	Понимание: — Извлечение параметров из сырого текста пользователя. На этом этапе система работает как Feature Extractor (экстрактор признаков). Текст очищается от эмоционального шума, из него выделяются ключевые переменные для поиска.
•	Вдохновение: — Формирование предложений при недостатке данных. Если пользователь ввел слишком размытый запрос, система активирует базу концептуальных направлений и предлагает 2-3 варианта для сужения фокуса поиска.
•	Подбор: — Программное обращение к мок-базе данных. Бэкенд забирает очищенные сущности из паспорта запроса и выполняет детерминированный поиск по файлам отелей, транспорта и активностей.
•	Объяснение: — Аргументация сформированной выдачи. Нейросеть сопоставляет извлеченные теги пользователя (например, спа, бассейн, тишина) со свойствами найденных объектов и генерирует короткий связный текст, объясняющий выгоду данного выбора.
•	Сборка: — Агрегация объектов в единый пакет. Система связывает найденные ID проживания, транспорта и трансфера в единую сущность — Корзину, производит математический пересчет итоговой стоимости и выводит графические карточки на фронтенд.
•	Пересборка: — Индивидуальная корректировка элементов. При получении команды на замену конкретного объекта (например, заменить поезд) система точечно перезапускает этап Подбора только для целевой сущности, сохраняя неизменным остальной контекст корзины.
3. Спецификация структуры данных (Паспорт Запроса)
В соответствии с принципом атомарности, описанным в индустриальной практике проектирования ИИ-систем, любое входящее сообщение должно быть нормализовано в фиксированный JSON-паспорт требования. Модель верхнего уровня (Pydantic-контракт) содержит следующие поля:
{
  "destination": "string or null", // Целевой город, регион или локация
  "start_date": "string (YYYY-MM-DD) or null", // Дата начала поездки
  "end_date": "string (YYYY-MM-DD) or null", // Дата окончания поездки
  "travelers_count": "integer", // Количество человек (по умолчанию 1)
  "budget_limit": "integer or null", // Максимальный бюджет в рублях
  "hotel_preferences": "array of strings", // Теги отеля (спа, бассейн, центр)
  "transport_preferences": "array of strings", // Теги транспорта (поезд, утро, без багажа)
  "is_vague_query": "boolean" // Флаг размытого запроса (0 или 1)
}
4. Сценарии использования (Use Cases)
Для синхронизации работы бэкенд-разработчиков и фронтендера ниже спроектированы три детальных сценария, включая сложные и проблемные кейсы, с которыми столкнется команда.
Сценарий 1. Полноценный прямой подбор (Основной успешный сценарий)
Условия: Пользователь сразу ввел достаточно данных для инициализации поиска.
•	1. Пользователь отправляет сообщение: «Хочу на вторые выходные ноября вдвоем в Карелию, отель обязательно с баней, бюджет 40к».
•	2. Бэкенд передает текст в LLM. LLM заполняет паспорт запроса: destination='Карелия', start_date='2026-11-14', end_date='2026-11-15', travelers_count=2, budget_limit=40000, hotel_preferences=['баня'], is_vague_query=false.
•	3. Бэкенд проверяет паспорт. Так как локация и даты присутствуют, система минует этап Вдохновения и вызывает функцию подбора из базы данных моков.
•	4. LLM получает сырые данные найденных объектов (Отель 'Ладога Спа' ID 4, Поезд 'Ласточка' ID 8) и генерирует текст: 'Я подобрал отель Ладога Спа, так как там есть баня, и утренний поезд, чтобы вы приехали к заселению'.
•	5. Бэкенд упаковывает объекты в единую корзину, суммирует цены и отправляет на фронтенд JSON, содержащий текст ответа и массив карточек. Фронтенд красиво рендерит чат и корзину.
Сценарий 2. Абстрактный запрос (Включение этапа Вдохновения)
Условия: Пользователь не знает, куда поехать, параметры неочевидны.
•	1. Пользователь отправляет сообщение: «Я очень устал от работы, хочу уехать отдохнуть на пару дней туда, где красивая природа».
•	2. LLM парсит текст и заполняет паспорт: destination=null, hotel_preferences=['природа', 'отдых'], is_vague_query=true. Даты и локация отсутствуют.
•	3. Бэкенд видит флаг is_vague_query=true. Поиск по базе отелей блокируется. Переход на этап Вдохновения.
•	4. LLM обращается к текстовому справочнику направлений и выдает в чат интерактивные варианты: 'Вариант 1: Уединенные эко-отели в лесах Карелии', 'Вариант 2: Купеческие усадьбы и тишина Золотого Кольца'.
•	5. Пользователь нажимает на кнопку или пишет текстом: 'Давай Карелию'.
•	6. Система записывает destination='Карелия' в контекст памяти сессии, переводит флаг is_vague_query в false и возвращается к шагу 3 Основного сценария (Подбор).
Сценарий 3. Проблемный кейс пересборки с конфликтом ограничений (Смена условий)
Условия: Пользователь пытается точечно изменить элемент готовой корзины, но его новые требования технически несовместимы с текущим состоянием системы или лимитами.
•	1. В сессии уже собрана корзина: Отель 'Парк-Отель' (30 000 руб.) + Поезд (5 000 руб.) = Итого 35 000 руб. Бюджетный лимит пользователя — 40 000 руб.
•	2. Пользователь пишет в чат команду пересборки: «Замените мне поезд на перелет самолетом, не хочу долго ехать».
•	3. Бэкенд распознает намерение изменения транспорта. Система обращается к мокам авиабилетов. Минимальная цена авиабилета на эти даты в базе составляет 12 000 руб.
•	4. Программный модуль бэкенда производит тестовый пересчет корзины: Отель (30 000) + Самолет (12 000) = 42 000 руб. Программа фиксирует Проблему: превышен жесткий лимит бюджета пользователя (42 000 > 40 000).
•	5. Обработка ошибки (Бизнес-логика защиты от тупика): Вместо падения в ошибку или молчаливой замены бэкенд передает этот контекст конфликта в LLM.
•	6. LLM генерирует предупреждающий компромиссный ответ: 'Я нашел авиабилеты за 12 000 рублей, но в таком случае общая стоимость тура составит 42 000 рублей, что превышает ваш лимит в 40 000 рублей. Мы можем либо превысить бюджет, либо я подберу вам отель дешевле, чтобы уложиться в рамки. Как поступим?'. Корзина на фронтенде остается заблокированной в старом состоянии до явного выбора пользователя.
