# Skrinio Travel Agent — Бизнес-контекст и Архитектура системы

Настоящая документация определяет бизнес-логику, функциональные этапы и архитектурный паттерн ИИ-ассистента «Skrinio» в рамках хакатона Ostrovok 2026 (трек «О!дин запрос»).

## 1. Бизнес-контекст и Пользовательские истории

Основная задача системы — трансформация хаотичных текстовых и голосовых запросов пользователей в детерминированную структуру данных для автоматического подбора туров без риска галлюцинаций языковой модели.

### User Story
Как самостоятельный путешественник, я хочу отправить один текстовый или голосовой запрос на естественном языке, содержащий мои хаотичные пожелания, чтобы мгновенно получить сбалансированный, посчитанный тур (билеты, проживание, трансфер) с интерактивной картой отелей и прозрачным объяснением выбора, не тратя время на ручной поиск по десяткам разрозненных сайтов.

---

## 2. Функциональные требования по 6 этапам работы агента

Взаимодействие ИИ-агента с пользователем и базой данных разбито на шесть последовательных технологических этапов:

1. **Понимание:** Извлечение параметров из сырого текста или транскрипта речи (Feature Extraction). Текст очищается от эмоционального шума, из него выделяются ключевые переменные для поиска.
2. **Вдохновение:** Формирование предложений при недостатке данных. Если пользователь ввел размытый запрос, система активирует базу концептуальных направлений и предлагает варианты для сужения фокуса.
3. **Подбор:** Программное обращение к In-Memory Mock DB. Бэкенд забирает очищенные сущности из Паспорта Запроса и выполняет детерминированный поиск по отелям, транспорту и активностям.
4. **Объяснение:** Аргументация сформированной выдачи. Нейросеть сопоставляет извлеченные теги пользователя со свойствами найденных объектов и генерирует короткий связный текст, объясняющий выгоду выбора.
5. **Сборка:** Агрегация объектов в единый пакет. Система связывает найденные ID проживания, транспорта и трансфера в Корзину, производит математический пересчет итоговой стоимости и выводит графические карточки на фронтенд.
6. **Пересборка:** Индивидуальная корректировка элементов. При команде на замену конкретного объекта система точечно перезапускает этап Подбора только для целевой сущности, сохраняя остальной контекст корзины.

## 3. Архитектурный паттерн: Детерминированный Конечный Автомат (State Machine)

Система спроектирована на основе детерминированного конечного автомата, развернутого поверх большой языковой модели (LLM). Вся логика переходов между состояниями зашита на уровне бэкенд-кода, что исключает неконтролируемое ветвление на стороне LLM.

### Алгоритм обработки сообщения (Запрос — Ответ):
1. **Извлечение признаков:** Бэкенд передает сырой текст пользователя в LLM. Используется специальный системный промпт для семантического парсинга (Slot Filling). LLM возвращает заполненный JSON Паспорта Запроса.
2. **Детерминированная валидация:** Бэкенд принимает JSON Паспорта и программными средствами (Pydantic-валидаторы на уровне Go/Python) проверяет обязательные поля: `destination` (локация) и `dates` (даты).
3. **Маршрутизация:**
   * **Ветка А (Состояние `inspiration`):** Если хотя бы одно из критических полей равно `null`, поиск блокируется. LLM генерирует наводящий или уточняющий вопрос.
   * **Ветка Б (Состояние `searching`):** Если поля заполнены, бэкенд активирует механизм **Function Calling**, передавая в API массив описаний поисковых инструментов.

### Механизм Function Calling и перехват управления:
1. LLM анализирует Паспорт Запроса и возвращает структуру `tool_calls` с именем требуемой функции и заполненными аргументами JSON.
2. Бэкенд прерывает выполнение LLM, перехватывает управление и локально выполняет код функции, обращаясь к изолированной In-Memory Mock DB.
3. Результат выполнения функции бэкенд упаковывает в сообщение с ролью `tool` и отправляет обратно в LLM.
4. LLM анализирует данные от функции, формирует финальный текстовый ответ (объяснение выбора) и итоговую структуру корзины для фронтенда.
