# Спецификация технического задания на контейнеризацию и развертывание проекта

Настоящий технический регламент фиксирует требования к сборке, безопасности и локальному развертыванию прототипа AI-агента для путешествий «Skrinio» в рамках хакатона Ostrovok 2026 (трек «О!дин запрос»).

## 1. Назначение и цель задачи
Обеспечить запуск всего программного комплекса (фронтенд и бэкенд) одной POSIX-совместимой командой `docker compose up --build` на локальной машине проверяющего. 

Локальное объединение в единый сетевой контур устраняет проблему Mixed Content (блокировку безопасности браузера), возникающую при попытке публичного фронтенда (`https://vercel.app`) обратиться к локальному бэкенду (`http`).

## 2. Архитектурное решение (Совмещенный рантайм)
В рамках локального демонстрационного сценария Go-бэкенд принимает на себя роль единой точки входа и сервера статики (Reverse Proxy & Static File Server):
*   **Порт приложения:** Процесс внутри контейнера слушает порт `8080`.
*   **Корневой маршрут (`GET /`):** Бэкенд раздает скомпилированные статические файлы веб-интерфейса (HTML, JS, CSS) из локальной директории `./static`.
*   **Маршруты API (`/api/v1/*`):** Обрабатываются Go-микросервисами (стриминг ответов через Server-Sent Events, семантический парсинг, Function Calling).
*   **База данных:** Данные отелей и транспорта хранятся в In-Memory Mock DB в оперативной памяти бэкенда и автоматически сидируются на русском языке при старте.

## 3. Матрица ответственности разработчиков

### Требования к фронтенду:
1.  **Изоляция исходного кода:** Перенести все файлы интерфейса в выделенную подпапку `/frontend` в корне репозитория.
2.  **Локализация API:** Перевести базовый URL запросов (Base URL) сетевого клиента на относительный путь `/api/v1` (вместо абсолютного адреса Vercel).
3.  **Стандартизация билда:** Команда `npm run build` должна генерировать автономную сборку в директорию `/dist` или `/build`.

### Требования к бэкенду:
1.  **Static Server в Go:** Добавить в роутер обработку статики: `router.Handle("/", http.FileServer(http.Dir("./static")))`.
2.  **Проверка работоспособности:** Реализовать обязательный эндпоинт `GET /health`, возвращающий статус `200 OK` и JSON `{"status": "ok"}`.
3.  **Конфигурация:** Все системные порты и ключи API (LLM) должны считываться строго из переменных окружения.

## 4. Регламент DevOps и Безопасности
*   **Multi-stage сборка:** Итоговый Dockerfile должен собираться в 3 этапа (сборка фронтенда в Node -> компиляция Go бэкенда -> финальный чистый рантайм в Alpine Linux). Это гарантирует легкий вес образа (лимит развертки <= 10 минут) и отсутствие лишних dev-инструментов.
*   **Запуск без root-прав:** Внутри финального контейнера Alpine запрещено выполнять процессы от пользователя root. Необходимо принудительно создать ограниченного пользователя (например, `appuser`) и передать ему права на директорию `/app`.
*   **Фиксация платформ:** В файле `docker-compose.yml` должна быть жестко зафиксирована платформа `platform: linux/amd64` для обеспечения кроссплатформенности на ноутбуках жюри.
*   **Автоматический Healthcheck:** Внедрить в Compose проверку готовности контейнера через утилиту `wget` или `curl` к эндпоинту `http://localhost:8080/health`.
*   **Логирование:** Приложение обязано писать все системные логи напрямую в потоки `stdout` и `stderr`, чтобы они были доступны для отладки через команду `docker compose logs app`.
