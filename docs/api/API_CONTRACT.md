# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: АРХИТЕКТУРА AI-АГЕНТА И ИНТЕГРАЦИОННЫЕ API-КОНТРАКТЫ

Настоящая техническая спецификация определяет архитектурную логику, протоколы обмена данными, форматы запросов для гибридного интерфейса, интерактивной карты, голосового ввода, а также механизмы семантического парсинга и ведения заметок в рамках проекта AI-агента для путешествий «Skrinio» на хакатоне Ostrovok 2026.

---

## 1. НАЗНАЧЕНИЕ ДОКУМЕНТА И АРХИТЕКТУРНЫЙ ПАТТЕРН

Система проектируется на основе детерминированного конечного автомата (Deterministic State Machine), развернутого поверх большой языковой модели (LLM). Детерминированный конечный автомат на уровне бэкенд-кода осуществляет жесткую валидацию промежуточных структур данных (Паспорта Запроса) и управляет переходами между состояниями. Это полностью исключает неконтролируемое поведение или самостоятельное ветвление логики на стороне LLM.

### 1.1 Архитектура голосового ввода
*   **Логика на фронтенде:** Распознавание речи полностью вынесено на сторону клиента через браузерное Web Speech API (SpeechRecognition). Фронтенд локально транскрибирует аудиопоток в текст, автоматически вставляет результат в инпут чата и отправляет его на бэкенд в рамках стандартного текстового запроса (поле `text_query`).
*   **Логика на бэкенде:** Полный отказ от локальных библиотек распознавания звука и тяжелых ML/NER-моделей на Go. Это исключает риск нарушения ограничений хакатона на размер образа и лимит развертки (<=10 минут). Семантический парсинг (извлечение сущностей) делегируется внешней LLM через OpenAI-совместимый API с помощью системного промпта.

## 2. ВЕРХНЕУРОВНЕВЫЙ СЦЕНАРИЙ РАБОТЫ И FUNCTION CALLING

### 2.1 Алгоритм обработки входящего сообщения (Запрос — Ответ)
Каждое текстовое сообщение пользователя, отправленное из интерфейса чата, обрабатывается на бэкенде в рамках строгого сквозного цикла, состоящего из пяти микро-шагов:
1. **Извлечение признаков (Intent Extraction & Slot Filling).** Бэкенд передает сырой текст пользователя и текущий контекст диалога в LLM. Используется специальный системный промпт и JSON-схема Паспорта Запроса. LLM выполняет семантический парсинг, извлекает параметры и возвращает заполненный или обновленный JSON Паспорта Запроса.
2. **Детерминированная валидация.** Бэкенд принимает JSON Паспорта Запроса и программными средствами (через Pydantic-валидаторы на уровне кода, без участия нейросети) проверяет обязательные для поиска поля: `destination` (локация) и `dates` (даты).
3. **Маршрутизация (Ветвление состояний).** На основании результатов валидации бэкенд определяет ветку выполнения. Если хотя бы одно из критических полей равно null, система переходит в Ветку А (Состояние `inspiration`). Если оба критических поля заполнены, система переходит в Ветку Б (Состояние `searching`).
    *   **Ветка А (Состояние `inspiration`).** Бэкенд блокирует вызов поисковых инструментов, передает Паспорт Запроса в LLM и заставляет модель сгенерировать естественный наводящий или уточняющий вопрос для пользователя. Сгенерированный текст возвращается на фронтенд.
    *   **Ветка Б (Состояние `searching`).** Бэкенд активирует механизм Function Calling, передавая в OpenAI-совместимый API массив описаний доступных программных функций для поиска по мок-базе данных.

### 2.2 Механизм Function Calling и Спецификация Инструментов
Function Calling — технология, при которой языковая модель на основе контекста принимает решение вызвать внешнюю программную функцию, формируя для нее аргументы в формате JSON, но само непосредственное выполнение функции происходит на стороне бэкенда.

Для обеспечения работы пилотного региона бэкенд объявляет три системных инструмента (Tools):
*   `search_hotels(location: str, start_date: str, end_date: str, hotel_tags: list[str]) -> list[json]` — функция осуществляет поиск доступных отелей по геолокации, временному интервалу и тегам атмосферы.
*   `search_transports(location: str, start_date: str, end_date: str, budget_limit: float) -> list[json]` — функция осуществляет поиск доступных билетов или трансферов до точки назначения и обратно.
*   `calculate_total_cart(hotel_id: str, transport_id: str) -> json` — техническая функция расчета итоговой стоимости единой корзины с программной проверкой лимитов.

**Порядок перехвата управления бэкендом (Execution Flow):**
1. LLM анализирует Паспорт Запроса и возвращает структуру `tool_calls` с именем требуемой функции и заполненными аргументами JSON.
2. Бэкенд прерывает выполнение LLM, перехватывает управление и локально выполняет код вызванной функции, обращаясь к изолированной мок-базе пилотного региона.
3. Результат выполнения функции (массив объектов) бэкенд упаковывает в техническое сообщение с ролью `tool` и отправляет обратно в LLM.
4. LLM анализирует полученные от функции данные, формирует финальный текстовый ответ для пользователя (аргументированное объяснение выбора) и итоговую структуру корзины.

## 3. ЛОГИКА УПРАВЛЕНИЯ КОНТЕКСТОМ И ПАМЯТЬЮ СЕССИИ

Ввиду stateless-природы протокола HTTP, обязанность по сквозному хранению истории чата, параметров Паспорта и состояния корзины возлагается на бэкенд. Память сессии организуется в виде структуры In-Memory Session Storage (синглтон-словарь в оперативной памяти бэкенда), где уникальным ключом выступает `session_id` в формате UUID v4.

### 3.1 Структура хранения данных в памяти сессии (SessionData)
Каждая сессия описывается строго фиксированной схемой данных:
*   `session_id`: Строка (UUID v4) — уникальный маркер сессии диалога.
*   `passport`: Объект, содержащий `location` (строка/null), `dates` (объект `start_date` и `end_date` формата YYYY-MM-DD/null), `budget_limit` (число/null), `hotel_tags` (массив строк).
*   `cart`: Объект текущей сборки тура, содержащий в себе вложенные объекты:
    *   `hotel`: (id строки, name строки, price числа, start_date строки, end_date строки, массив tags).
    *   `transport`: (id строки, type строки, price числа, departure_date строки).
    *   `total_price`: числовая сумма активных позиций.
    *   `status`: строка-статус (`empty`, `valid`, `budget_exceeded`).
*   `chat_history`: Массив объектов сообщений для передачи в LLM, где каждый элемент содержит `role` (`user`, `assistant`, `system`, `tool`) и `content` (строка текста).

### 3.2 Жизненный цикл контекста при сценариях пересборки (Изоляция изменений)
При обработке Use Case «Проблемный кейс пересборки» (когда пользователь просит точечно заменить один компонент, например, вид транспорта), бэкенд реализует алгоритм изоляции состояний:
1. **Считывание текущего состояния:** Бэкенд извлекает объект `SessionData` по `session_id` из оперативной памяти.
2. **Атомарное обновление Паспорта:** Новое сообщение пользователя («замени транспорт на самолет») отправляется в LLM исключительно для извлечения новых локальных намерений. Базовые поля Паспорта (`location`, `dates`, `hotel_tags`) не затираются, а берутся из кэша сессии.
3. **Программная валидация бизнес-правил:** Бэкенд вызывает инструмент `search_transports` с фильтрацией по типу транспорта. Получив от мок-базы новый вариант (например, авиабилет стоимостью 60 000 рублей), внутренний программный валидатор бэкенда выполняет математическое сложение: Цена отеля (80 000) + Цена нового транспорта (60 000) = 140 000 рублей. Проводится сверка с `budget_limit` (150 000). Лимит соблюден, данные корзины `cart` перезаписываются.
4. **Обработка конфликта лимитов:** Если стоимость нового компонента приводит к превышению `budget_limit`, бэкенд блокирует перезапись рабочего состояния корзины в памяти сессии (сохраняется предыдущий валидный тур). Контексту корзины временно присваивается статус `conflict_budget`. Бэкенд отправляет в LLM системную директиву: «Сгенерируй отказ в замене, укажи точную сумму превышения и предложи компромисс». На фронтенд возвращается сообщение об ошибке (статус `conflict`), стабильность системы сохраняется.

## 4. СПЕЦИФИКАЦИЯ ИНТЕРФЕЙСНОГО ВЗАИМОДЕЙСТВИЯ (API CONTRACT)

### 4.1 Основной метод чата: POST /api/v1/chat/message
Контракт поддерживает одновременную передачу сырого текста/транскрипта и структурированных данных стартовой формы. Бэкенд возвращает ответ в формате Server-Sent Events (SSE). В ответе передаются явные float-координаты для интерактивной карты.

#### Тело запроса (Request JSON от Фронтенда к Бэкенду):
```json
{
  "session_id": "string or null",
  "text_query": "string",
  "quick_filters": [
    "+ подешевле"
  ],
  "form_data": {
    "destination": "Казань",
    "check_in": "2026-11-14",
    "check_out": "2026-11-16",
    "guests": {
      "adults": 2,
      "children": 0
    }
  }
}
```

#### Тело ответа (Response JSON — агрегированный чанк SSE от Бэкенда к Фронтенду):
```json
{
  "session_id": "string",
  "text_chunk": "string",
  "is_final": false,
  "current_state": "searching",
  "cart": {
    "hotels": [
      {
        "id": "hotel_ostrovok_comfort_kazan",
        "name": "Отель Полянка Комфорт",
        "price_per_night": 6500.00,
        "rating": 4.5,
        "coordinates": {
          "latitude": 55.796123,
          "longitude": 49.106414
        },
        "justification": "Хвалят за тишину и близость к центру"
      }
    ],
    "total_price": 13000.00,
    "status": "valid"
  }
}
```
* Допустимые значения `current_state`: `inspiration`, `searching`, `conflict`, `completed`.*
* Допустимые значения `cart.status`: `empty`, `valid`, `budget_exceeded`, `conflict_budget`.*

### 4.2 Логика сохранения версий чата (Снапшоты сессии)
Функционал позволяет пользователю делать слепки текущего состояния диалога и корзины, фиксируя успешные итерации подбора, а также удалять ненужные версии.

*   **Сохранение текущей версии чата:**
    *   **Маршрут:** `POST /api/v1/snapshots`
    *   **Тело запроса:**
    ```json
    {
      "session_id": "string (UUID)",
      "title": "Найти апартаменты недолеко отцентра Казани..."
    }
    ```
    *   **Логика бэкенда:** Сервер дублирует текущую структуру `SessionData` (историю сообщений и состав корзины) под новым `snapshot_id`.
    *   **Ответ (201 Created):** `{"status": "snapshot_created", "snapshot_id": "string"}`

*   **Удаление сохраненной версии:**
    *   **Маршрут:** `DELETE /api/v1/snapshots/{snapshot_id}`
    *   **Ответ (200 OK):** `{"status": "deleted"}`

### 4.3 Логика интерактивного блокнота (Заметок)
Функционал заметок изолирован от основного контекста LLM чата и представляет собой CRUD-механизм хранения текстовых блоков пользователя. Заметки привязываются к `session_id`. Пользователь может скопировать туда любой фрагмент ответа ИИ или внести запись вручную.

*   **Сохранение/Создание новой заметки:**
    *   **Маршрут:** `POST /api/v1/notes`
*   **Получение списка сохраненных элементов:**
    *   **Маршрут:** `GET /api/v1/notes?session_id=...`

## 5. МАТРИЦА ЗОН ОТВЕТСТВЕННОСТИ КОМПОНЕНТОВ

### 5.1 Фронтенд
*   **Инициализация и сохранение сессии:** Отвечает за проверку наличия `session_id` в LocalStorage браузера. При первом запуске передает null, перехватывает сгенерированный сервером UUID и сохраняет его для последующих запросов.
*   **Интерфейсная блокировка (UI Lock):** На время отправки запроса и ожидания HTTP-ответа полностью блокирует кнопку отправки и поле ввода чата, отображая анимацию загрузки.
*   **Раздельный рендеринг:** Текстовый контент из `message.content` выводится строго в диалоговое окно чата. Объект `cart` рендерится исключительно в правом графическом виджете корзины (включая float-координаты для интерактивной карты). Блокнот заметок выносится в боковой раскрывающийся виджет. Фронтенд не производит никаких математических расчетов стоимости, а лишь отображает готовые поля из JSON.
*   **Управление индикацией ошибок:** Приполучении статуса `cart.status` со значением `budget_exceeded` или `conflict_budget` фронтенд подсвечивает виджет корзины критическим цветом и выводит предупреждение о нарушении лимита.

### 5.2 Бэкенд
*   **Управление сессиями:** Выделяет изолированные структуры в оперативной памяти под новые UUID, считывает историю диалога для существующих сессий. Реализует эндпоинты сохранения снапшотов чата и стандартные HTTP-методы CRUD для заметок.
*   **Слой взаимодействия с LLM:** Формирует контекст, отправляет запросы к OpenAI-совместимый API, отвечает за десериализацию ответов в структурированные сущности. Полностью отказывается от локальных библиотек распознавания звука на Go.
*   **Программное управление графом состояний:** Обеспечивает логику ветвления на основе валидации Паспорта Запроса. Принимает решение о переходе между состояниями на уровне серверного кода.
*   **Слой выполнения инструментов и Mock-данных:** Хранит статичные и моковые структуры данных по отелям и транспорту, осуществляет фильтрацию по аргументам, переданным из механизма Function Calling.
*   **Математическая валидация бизнес-правил:** Вычисляет суммарную стоимость корзины, проверяет соблюдение лимитов бюджета, присваивает итоговые статусы валидности корзины.

## 6. РЕГЛАМЕНТ ОБРАБОТКИ ИСКЛЮЧИТЕЛЬНЫХ СИТУАЦИЙ И СИСТЕМНЫЕ ПРОМПТЫ

### 6.1 Алгоритм обработки пустых результатов мок-базы
Если внутренний метод бэкенда (`search_hotels` или `search_transports`) возвращает пустой массив `[]` ввиду отсутствия свободных мест или несовпадения тегов атмосферы, бэкенд обязан выполнить программный перехват:
1. Бэкенд формирует для LLM техническое сообщение с ролью tool: `'Error: No hotels found for criteria: Karelia, dates: 2026-07-01 - 2026-07-08, tags: ['spa']'`.
2. Модель анализирует ошибку и на основании системного промпта генерирует тексто предложение компромисса (например, предлагает изменить даты или отказаться от тега).
3. Бэкенд упаковывает ответ, выставляя `current_state`: `'inspiration'` и `cart`: `null`, после чего отправляет JSON на фронтенд.

### 6.2 Промпт для семантического парсинга (Slot Filling)
Вызывается бэкендом как атомарный нестриминговый запрос перед валидацией:
```text
ROLE: You are a strict Feature Extractor for the Skrinio Travel Agent.
TASK: Analyze the user's raw text or voice transcript and extract entities into the required JSON schema.
CONSTRAINTS:
1. Output ONLY a valid JSON object. Do not include any markdown formatting, explanations, or conversational filler.
2. If an entity is not explicitly mentioned or cannot be confidently inferred, set its value to null.
3. Normalize all relative dates (e.g., 'next weekend', 'for 3 days') into exact YYYY-MM-DD formats relative to the current date: 2026-10-27.
4. Convert budget values to clear integers.
5. Map verbal preferences to strict text tags on Russian language.
JSON SCHEMA:
{
  "destination": "string or null",
  "start_date": "string (YYYY-MM-DD) or null",
  "end_date": "string (YYYY-MM-DD) or null",
  "travelers_count": integer (default 1),
  "budget_limit": integer or null,
  "hotel_preferences": ["string"],
  "is_vague_query": boolean
}
```

### 6.3 Жесткий Системный Промпт ядра (System Prompt Orchestrator)
Зашивается бэкендом как первое сообщение с ролью `system` в историю чата:
```text
РОЛЬ: Вы — Ядро Оркестрации AI-агента для путешествий Островка (Orchestrator Core of the Ostrovok Travel AI Agent).
ОГРАНИЧЕНИЯ:
1. Запрещено придумывать отели, транспорт, цены или направления, которых нет в ответах предоставленных инструментов.
2. Ваша единственная цель — заполнить слоты в Паспорте Пользователя (User Passport): местоположение (location), даты (dates), лимит бюджета (budget_limit), теги отеля (hotel_tags).
3. Если в Паспорте Пользователя отсутствуют 'location' (местоположение) или 'dates' (даты), вы ОБЯЗАНЫ задать уточняющие вопросы. В этом случае не вызывайте инструменты поиска.
4. При вызове инструментов используйте точные значения из Паспорте Пользователя.
5. Если инструмент возвращает пустой список или ошибку, объясните проблему пользователю и предложите изменить теги, бюджет или даты.
6. Никогда не выводите markdown-таблицы. Возвращайте ответы только в виде текстовых объяснений.
```
